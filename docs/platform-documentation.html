1. Arquitectura General y Topología

ikedadev-platform sigue una estrategia de microservicios desacoplados con base de datos lógica independiente por servicio (Database-per-Service) alojados dentro de un único monorepo Cargo Workspace. Cada servicio expone su propio contrato /openapi.json y su UI interactiva /swagger-ui, compila en un binario nativo ligero y corre en contenedores multi-stage (cargo-chef + Debian Bookworm / Distroless).

Clean Architecture Estricta en Cada Servicio

1. domain/

Entidades puras, enums polimórficos, invariantes de negocio y traits (puertos). Cero imports de SQLx, Axum o Reqwest.

2. application/

Casos de uso atómicos (Create...UseCase, Search...UseCase) que orquestan puertos y reglas de negocio. 100% testeables con mocks.

3. infrastructure/

Adaptadores concretos: repositorios SQLx con transacciones RLS, traductores Criteria ➔ SQL, cliente Keycloak y QStash.

4. presentation/

Handlers Axum delgados, AppState con FromRef, documentación utoipa y enrutamiento REST + Swagger UI.

2. Librería Compartida: crates/ikeda-core

Contiene todos los contratos transversales para garantizar que cada API presente y futura hable exactamente el mismo idioma HTTP, de errores, paginación y seguridad.

MóduloComponentes ClaveResponsabilidad
response ApiResponse<T>, PaginatedApiResponse<T>, PaginationMeta Envoltorio JSON uniforme (success, message, data, pagination, timestamp ISO-8601) con ToSchema e IntoResponse.
error AppError, ValidationErrorDetail Mapeo exhaustivo con thiserror a códigos HTTP (400, 401, 403, 404, 409, 422, 500) enmascarando detalles internos de DB hacia el cliente.
criteria Criteria, FilterGroup, FilterRule, FilterOperator, OrderBy, Pagination Árbol recursivo AND/OR serializable y compatible con OpenAPI para búsquedas dinámicas seguras.
tenant TenantContext, ApiKeyValidator, CachedApiKeyValidator, JwtValidator, JwksJwtValidator Extractor Axum FromRequestParts con prioridad estricta: 1) X-Api-Key (SHA-256 + caché 60s), 2) Bearer JWT (RS256 JWKS), 3) dev-auth (solo compilando con feature).
observability init_tracing, http_trace_layer, request_id_layer, REQUEST_ID_HEADER Tracing estructurado en json (por defecto, compatible con Loki y Cloud Logging) o pretty vía LOG_FORMAT y RUST_LOG (default info,tower_http=info,sqlx=warn). Propaga/genera X-Request-Id y registra latencia y tenant_id sin exponer Authorization, X-Api-Key ni Cookie.

5. Microservicio: services/crm-api Puerto 8081

Base de datos centralizada de clientes finales de cada tenant. Garantiza unicidad de email y tax_id (RUT / DNI / VAT) por tenant ignorando registros con Soft Delete, y permite vincular clientes con cuentas de portal (keycloak_user_id).

Método y RutaFuncionalidad Principal
POST /v1/clientsCrea cliente final (409 Conflict si email o tax_id ya existe activo en el mismo tenant; dos tenants distintos sí pueden tener el mismo RUT/email).
GET / PATCH / DELETE /v1/clients/{id}Consulta, actualización parcial validando unicidad y Soft Delete (libera el RUT/email para recreación futura).
POST /v1/clients/searchBúsqueda paginada con Criteria recursivo traducido a sqlx::QueryBuilder (columnas estándar + metadata.<key> indexado con GIN).

6. Microservicio: services/catalog-api Puerto 8083

Catálogo comercial polimórfico que unifica Servicios (con duración y buffer para agendar), Productos (físicos o digitales con inventario opcional) y Bundles/Paquetes (combinación de múltiples ítems). Todos los precios se almacenan en BIGINT (unidad mínima de moneda, ej. CLP o centavos) e impuestos en basis points (1900 = 19%).

Método y RutaFuncionalidad Principal
POST / GET /v1/categoriesCrea y lista categorías jerárquicas (parent_id, slug único por tenant, display_order).
PATCH / DELETE /v1/categories/{id}Actualización parcial y Soft Delete de categorías.
POST /v1/itemsCrea ítems polimórficos (item_type: "SERVICE" | "PRODUCT" | "BUNDLE") validando duración obligatoria para servicios, SKU único y existencia de componentes en bundles.
GET / PATCH / DELETE /v1/items/{id}Obtiene ítem hidratado con variantes activas y componentes de bundle; edición parcial y Soft Delete.
POST /v1/items/searchBúsqueda paginada con Criteria (incluye rangos de base_price, item_type, category_id y metadata.*).
POST /v1/items/batchConsulta en lote de hasta 100 IDs en una sola query SQL (ANY($1)) con hidratación batch de variantes y bundles para eliminar problemas N+1 en BFFs.
POST / PATCH / DELETE /v1/items/{id}/variants[/{variant_id}]Administra variantes (ej. "60 min", "90 min", "Talla M") con price_override y duration_override.

6b. Microservicio: services/bookings-api Puerto 8084

Fuente de verdad comercial de reservas multi-servicio, 100% agnóstica al rubro y desacoplada (usa referencias opacas por UUID a client_id, calendar_id, event_id, catalog_item_id y variant_id). Congela los snapshots de precios, impuestos y duración en booking_items con aritmética entera pura (BIGINT, sin floats) y soporta idempotencia transaccional de 24h vía Idempotency-Key.

Máquina de Estados Estricta (BookingStatus): PENDING ➔ SCHEDULED | CANCELLED · SCHEDULED ➔ IN_PROGRESS | COMPLETED | CANCELLED | NO_SHOW · IN_PROGRESS ➔ COMPLETED | CANCELLED | NO_SHOW · COMPLETED / CANCELLED / NO_SHOW son estados terminales (cualquier edición o transición adicional retorna 409 Conflict).
Método y RutaFuncionalidad Principal
POST /v1/bookingsCrea reserva multi-servicio calculando subtotal, tax_total, total_price y total_duration_minutes en enteros. Soporta header opcional Idempotency-Key (replay exacto o 409 Conflict si el payload difiere).
GET /v1/bookings/{id}Obtiene la reserva activa hidratada con sus booking_items congelados.
PATCH /v1/bookings/{id}Actualización parcial (fechas, calendario/evento, notas, metadata y reemplazo opcional de ítems recalculando totales). Rechaza con 409 si el estado es terminal.
PATCH /v1/bookings/{id}/statusTransiciona estado validando la máquina de estados, registra cancellation_reason / cancelled_at o completed_at y hace merge opcional en metadata.
DELETE /v1/bookings/{id}Soft Delete (deleted_at = NOW()).
POST /v1/bookings/searchBúsqueda paginada con Criteria (booking_code, client_id, calendar_id, event_id, status, starts_at, ends_at, total_price, currency y metadata.*) hidratando booking_items en lote (ANY($1), cero N+1).

7. Cómo se Espera que se Use (Patrón BFF y Contratos OpenAPI)

La plataforma está diseñada para operar bajo el patrón Backend-for-Frontend (BFF) o consumo directo autenticado:

A. Integración vía BFF dedicado (ej. anami-bff)

  • El frontend (React / Astro / Angular) nunca conoce las URLs internas de los microservicios ni almacena API Keys.
  • El BFF autentica al usuario final con Keycloak (o sesión), propaga X-Request-Id y orquesta llamadas paralelas hacia catalog-api, events-api, bookings-api, crm-api y telemetry-api (con compensación automática y auditoría asíncrona AUDIT).
  • Para llamadas M2M el BFF envía X-Api-Key: ik_live_...; para acciones a nombre del usuario reenvía Authorization: Bearer <jwt>.
  • Usa POST /v1/items/batch para enriquecer agendas o carritos sin caer en N+1.

B. Contratos OpenAPI como Fuente de Verdad

  • Cada servicio expone su esquema vivo en GET /openapi.json y su documentación interactiva en GET /swagger-ui.
  • Los BFFs en TypeScript o frontends generan tipos estrictos automáticamente:
npx openapi-typescript http://localhost:8083/openapi.json -o src/types/catalog-api.d.ts
npx openapi-typescript http://localhost:8080/openapi.json -o src/types/events-api.d.ts
npx openapi-typescript http://localhost:8081/openapi.json -o src/types/crm-api.d.ts
npx openapi-typescript http://localhost:8084/openapi.json -o src/types/bookings-api.d.ts
npx openapi-typescript http://localhost:8085/openapi.json -o src/types/telemetry-api.d.ts
Orden de Autenticación en TenantContext: 1) Si viene X-Api-Key, se hashea con SHA-256 y se valida en caché (60s) contra identity_db. 2) Si viene Authorization: Bearer <token>, se valida firma RS256 + exp + iss vía JWKS y se extrae el claim tenant_id. 3) Solo si se compila con --features dev-auth se aceptan headers X-Tenant-Id locales. En producción, cualquier X-Tenant-Id sin credencial válida es ignorado y rechazado con 401 Unauthorized.

8. Casos de Uso de Ejemplo (End-to-End)

Caso 1: Reserva Online en Spa / Centro Estético (anami-bff)

1
Listar servicios destacados: El BFF consulta POST /v1/items/search en catalog-api filtrando por item_type = "SERVICE" y metadata.featured = "true". Obtiene servicios hidratados con variantes (ej. Masaje 60 min $35.000 / 90 min $48.000).
2
Consultar horarios disponibles: Con la duración del servicio o variante (duration_override = 90), el BFF llama a GET /v1/calendars/{terapeuta_cal_id}/availability?slot_duration_minutes=90 en events-api.
3
Identificar o crear cliente: El BFF busca al cliente por RUT en crm-api (POST /v1/clients/search con tax_id = "12.345.678-9"). Si no existe, lo registra vía POST /v1/clients.
4
Confirmar reserva atómica e idempotente: El BFF envía POST /v1/events en events-api con header Idempotency-Key y metadata: { "client_id": "...", "catalog_item_id": "...", "variant_id": "..." }. Si el horario ya fue tomado, events-api responde 409 Conflict; si es exitoso, programa recordatorio vía Upstash QStash.

Caso 2: Onboarding Automatizado de un Nuevo Cliente SaaS (Tenant)

# 1. Crear Tenant (requiere scope platform:admin)
curl -X POST https://identity.ikedadev.com/v1/tenants \
  -H "X-Api-Key: $PLATFORM_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"slug": "anami-studio", "name": "Anami Wellness Studio", "config": {"plan": "pro"}}'

# 2. Emitir API Key para su BFF (devuelve raw_key UNA sola vez)
curl -X POST https://identity.ikedadev.com/v1/api-keys \
  -H "Authorization: Bearer $TENANT_ADMIN_JWT" \
  -H "Content-Type: application/json" \
  -d '{"name": "anami-bff-prod", "scopes": ["events:write", "crm:write", "catalog:read"]}'

# 3. Crear usuario administrador del cliente en Keycloak + tenant_users
curl -X POST https://identity.ikedadev.com/v1/users \
  -H "Authorization: Bearer $TENANT_ADMIN_JWT" \
  -H "Content-Type: application/json" \
  -d '{"email": "admin@anami.cl", "full_name": "Camila Soto", "roles": ["tenant:admin"], "send_invite_email": true}'

Caso 3: Clínica Médica — Agenda Recurrente con Cancelación Puntual

Un calendario configurado con allow_overlaps: false programa un bloque semanal de cirugía (rrule: "FREQ=WEEKLY;BYDAY=TU;COUNT=12"). Si el médico toma feriado un martes específico, el BFF invoca POST /v1/events/{id}/exceptions con {"original_starts_at": "2026-12-08T14:00:00Z", "is_cancelled": true}, liberando automáticamente esos slots en GET /v1/calendars/{id}/availability sin destruir la serie.

9. Motor Dinámico Criteria (Filtros Recursivos + JSONB)

Tanto crm-api, catalog-api, bookings-api como telemetry-api traducen el árbol recursivo Criteria de ikeda-core a SQL parametrizado seguro mediante sqlx::QueryBuilder, con listas blancas estrictas de columnas para eliminar cualquier riesgo de SQL Injection. 

POST /v1/items/search
{
  "filter": {
    "and": [
      { "field": "item_type", "operator": "eq", "value": "SERVICE" },
      { "field": "base_price", "operator": "gte", "value": 20000 },
      { "field": "base_price", "operator": "lte", "value": 50000 },
      { "field": "metadata.room", "operator": "eq", "value": "zen" }
    ]
  },
  "order_by": [{ "field": "base_price", "direction": "asc" }],
  "pagination": { "page": 1, "limit": 20 }
}

10. Seguridad Multi-Tenant en Profundidad

🛡️ PostgreSQL Row-Level Security (RLS)

Todas las tablas de negocio tienen ENABLE ROW LEVEL SECURITY y FORCE ROW LEVEL SECURITY. Cada repositorio abre una transacción y ejecuta SELECT set_config('app.current_tenant', $1, true). Si una consulta olvidara filtrar por tenant, PostgreSQL igualmente devuelve 0 filas.

🔑 Mínimo Privilegio en Neon PostgreSQL

En producción se crean roles sin BYPASSRLS: un rol de aplicación por servicio y un rol api_key_reader en identity_db que solo tiene permiso EXECUTE sobre la función SECURITY DEFINER authenticate_api_key(VARCHAR) — sin acceso SELECT a ninguna tabla. 

-- Ejecutar una vez en identity_db (Neon) para el connection string IDENTITY_DATABASE_URL:
CREATE ROLE api_key_reader LOGIN PASSWORD 'PASSWORD_SOLO_LECTURA' NOBYPASSRLS;
GRANT USAGE ON SCHEMA public TO api_key_reader;
GRANT EXECUTE ON FUNCTION authenticate_api_key(VARCHAR) TO api_key_reader;

-- Ejecutar una vez por servicio (events_db, crm_db, catalog_db, bookings_db, telemetry_db):
CREATE ROLE service_app LOGIN PASSWORD 'PASSWORD_SEGURO' NOBYPASSRLS;
GRANT USAGE ON SCHEMA public TO service_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO service_app;

11. Escalabilidad, Rendimiento y Hoja de Ruta

La plataforma fue diseñada para arrancar en capa gratuita ($0/mes) en Google Cloud Run + Neon PostgreSQL y escalar horizontalmente sin reescribir código.

DimensiónDiseño Actual (MVP Productivo)Evolución a Alta Escala
Cómputo Binarios Rust/Tokio stateless (~15-30 MB RAM en reposo), imágenes distroless/bookworm-slim en Google Cloud Run con scale-to-zero. Despliegue portable a Kubernetes / K3s (ARM64 o x86_64) usando los manifiestos Kustomize en deploy/k8s/base/ y Argo Workflows.
Autenticación JwksJwtValidator 100% stateless (caché 5m en RAM) + CachedApiKeyValidator (TTL 60s en RAM + pool ligero de 3 conexiones a identity_db). Invalidación instantánea de llaves revocadas vía pub/sub (Redis/NATS) si se requiere revocación sub-segundo entre decenas de réplicas.
Base de Datos 6 bases de datos lógicas desacopladas en Neon con índices parciales (WHERE deleted_at IS NULL) e índices GIN en metadata y properties. Separar instancias físicas por servicio, habilitar Neon Read Replicas para /search y particionamiento por tenant_id / fecha en events.
Consultas BFF Endpoint POST /v1/items/batch e hidratación SQL ANY($1) para eliminar consultas N+1. Caché HTTP/CDN en el BFF para catálogos públicos y eventos de dominio asíncronos (QStash / Kafka).
